# Отчет по тестированию и анализу граничных случаев в работе Party (Suslik Media)

## 1. Обзор и архитектура подсистемы Party

Подсистема совместного просмотра (Party / «Смотреть вместе») в Suslik Media распределена по трем платформам и серверному API:
- **Сервер:** `website/src/services/rooms.js`, `website/src/routes/rooms.js`, `website/src/routes/activity.js`.
- **Android:** `Party.kt`, `PartySyncEngine.kt`, `PlayerPartySync.kt`.
- **Desktop (Qt/C++):** `Party.cpp`, `PartySync.cpp`, `PlayerParty.cpp`.
- **Tizen (Samsung TV):** `party.js`, `partycore.js`.

Для проверки всех пограничных состояний был развернут и выполнен автоматизированный набор тестов (22 сценария), покрывающий как нормальные, так и стрессовые сценарии.

## 2. Правило «1 аккаунт = 1 активная комната / 1 устройство»

### 2.1. Логика работы
- Каждый клиент генерирует постоянный уникальный идентификатор устройства `client_id` (префиксы `an_`, `pc_`, `tv_` + 12 hex-символов), который сохраняется в локальном хранилище (`Store`/`SharedPreferences`/`localStorage`).
- На сервере поддерживается карта `accountActiveDevices: userId -> { clientId, roomId, at }`.
- Пользователи делятся на две категории:
  1. **Пользователи с аккаунтом** (`userId !== "shared"` и `userId !== "guest"`): для них действует строгое правило «1 аккаунт = 1 активное устройство и комната».
  2. **Пользователи по общему паролю** (`userId === "shared"`): несколько физических устройств могут находиться в одной или разных комнатах, однако каждое отдельное устройство идентифицируется по `client_id`.

### 2.2. Поведение в граничных случаях

| Сценарий | Ожидаемое поведение | Фактический результат проверки | Статус |
|---|---|---|---|
| **Смена устройства в той же комнате** (пользователь смотрел на ПК `pc_1`, затем вошел с телефона `phone_1`) | Старое устройство немедленно вытесняется (закрывается SSE-сокет), новое устройство регистрируется как активное. Если аккаунт был ведущим, права хоста переходят на новое устройство. | Вызов `POST /api/rooms/:id/join` вызывает `moveAccount`, закрывающий сокет `pc_1` и очищающий его из `members`. В `joinRoom` `phone_1` становится `host_client_id`. | **Работает штатно** |
| **Гонка переподключения старого устройства** (ПК после разрыва сокета пытается реконнектиться через 1 сек, пока телефон еще выполняет TLS-рукопожатие 2–5 сек) | Попытки старого устройства войти должны блокироваться кодом 403, приоритет сохраняется за новым устройством. | Гарантируется буфером ожидания `PENDING_DEVICE_TTL_MS = 30000`. Метод `findUserActiveRoom` видит несовпадение `normClientId !== activeDev.clientId` и возвращает 403 `other_device_same_room`. Клиент на 403 прекращает реконнекты. | **Работает штатно** |
| **Попытка входа одного аккаунта во 2-ю комнату** | Старая комната покидается автоматически, новое устройство подключается к новой комнате. | `moveAccount` находит участника во всех комнатах `rooms.values()` и вызывает `leaveRoom(oldRoom, oldClient, true)`. В старой комнате генерируется `member_left`. | **Работает штатно** |
| **Кратковременный сбой сети (тот же client_id)** | Переподключение с тем же `client_id` не должно вызывать ошибку «уже подключен». | В `findUserActiveRoom` проверка: `if (normClientId && member.client_id === normClientId) continue;`. Сервер обновляет `last_seen` и счетчик потоков `streams++`. | **Работает штатно** |
| **Несколько вкладок одного браузера** | Общий `client_id` (через `localStorage`). | Каждый `GET /events` увеличивает `member.streams`. Закрытие одной вкладки уменьшает счетчик (`streams--`). Участник удаляется из комнаты только при `streams === 0`. При нажатии кнопки «Выйти» (`force = true`) закрываются все потоки устройства. | **Работает штатно** |
| **Discord Activity + Плеер на ПК/телефоне** | Одновременное нахождение в Activity и в плеере не должно конфликтовать. | В Discord Activity пользователи добавляются в `room.watchers` («у пульта»), а плеер подключается к `room.members`. `findUserActiveRoom` проверяет только `room.members`, поэтому коллизий нет. | **Работает штатно** |

## 3. Автокик, очистка и удаление комнат / участников

### 3.1. Обрыв связи и уход участников
1. **Штатный выход (`POST /api/rooms/:id/leave`):**
   - Вызывает `leaveRoom(roomId, clientId, force = true)`.
   - Обнуляет `member.streams = 0`, закрывает сокет через `closeMemberStreams`.
   - Очищает активное устройство из `accountActiveDevices`.
   - Рассылает остальным событие `member_left` с отпечатком `clientKey(clientId)`.
2. **Аварийный обрыв соединения (TCP Close):**
   - Событие `res.on("close")` на маршруте `/api/rooms/:id/events` вызывает `leaveRoom(roomId, clientId, force = false)`.
   - В отличие от явного выхода, при обрыве связи `accountActiveDevices` **не очищается**, а обновляется через `touchAccountActiveDevice` — это дает вытесненному/оборванному устройству 30-секундное окно льготы для бесшовного возврата.
3. **«Тихий» обрыв сети (Half-Open TCP):**
   - Сервер каждые 20 секунд шлет SSE-комментарий `: ping\n\n`.
   - На сокете выставлен `req.socket.setKeepAlive(true, 10000)`.
   - Клиенты (в частности, Desktop-Qt) имеют `setTransferTimeout(60000)`. Если за 60 секунд пинг не пришел, клиент считает сокет мертвым и перезапускает соединение.

### 3.2. Автокик зависшей буферизации (`BUFFERING_LIMIT_MS`)
- Когда участник сообщает о начале буферизации (`handleRoomAction: buffering = true`), комната входит в состояние ожидания (`state.waiting = true`), время комнаты останавливается.
- **Граничный случай:** Что, если у участника намертво завис интернет или упал декодер?
- **Решение в коде:** Установлен лимит `BUFFERING_LIMIT_MS = 30 * 1000` (30 секунд). При расчете `updateWaiting` учитываются только те участники, у которых `now - buffering_since < 30000`. По истечении 30 секунд сервер автоматически сбрасывает `waiting = false`, и воспроизведение продолжается у всех остальных.
- **Досрочный сброс:** Если зависший участник закрыл приложение или вышел из комнаты, `leaveRoom` вызывает `updateWaiting(room)`, и ожидание снимается **немедленно**, без ожидания истечения 30 секунд.

### 3.3. Пауза пустой комнаты (`pauseIfEmpty`)
- Когда последний участник покидает комнату (`members.size === 0`), вызывается `pauseIfEmpty(room)`.
- Фиксируется расчетная позиция `pos = getEstimatedPos(state)`, флаги сбрасываются: `playing = false`, `waiting = false`. Время комнаты не «убегает» в пустоту.

### 3.4. Удаление комнат по таймауту (`sweepRooms`)
- Фоновый таймер запускается каждые 5 минут:
  - **Обычные комнаты:** `EMPTY_ROOM_TTL_MS = 30 * 60 * 1000` (30 минут после того, как опустели).
  - **Комнаты Discord Activity:** `CHANNEL_ROOM_TTL_MS = 5 * 60 * 1000` (5 минут после того, как опустели).
- Если комната была создана, но к ней так никто и не подключился по `/events`, поле `empty_since` выставляется в момент создания `createRoom`, поэтому «мертворожденные» комнаты также гарантированно удаляются через 30 минут.

## 4. Смена ведущих (Host Rotation & Transfer)

### 4.1. Автоматическая ротация при уходе хоста
1. **Льготный период (`HOST_GRACE_MS = 60000`):**
   - При уходе ведущего фиксируется `host_absent_since = Date.now()`.
   - Планируется таймер на 60 секунд.
   - Если ведущий восстановил связь в течение 60 секунд (`hostPresent(room) === true`), таймер аннулируется, ведущий сохраняет свои полномочия.
2. **Передача полномочий (`promoteIfHostGone`):**
   - Если через 60 секунд ведущий не вернулся, новым ведущим становится участник, дольше всех находящийся в комнате.
   - Очередность определяется автоматически: JavaScript `Map` (`room.members`) гарантирует порядок вставки (FIFO).
   - Рассылается событие `state_changed` с обновленным `host_id` и `host_key`.
   - Если прежний ведущий возвращается позже (например, через 5 минут), он заходит уже как обычный гость и не может перехватить управление назад.
3. **Ротация при общем пароле (`shared`):**
   - При `host_id === "shared"` ведущего отличает только `host_client_id`.
   - При ротации `setHost` перезаписывает `host_client_id` идентификатором нового участника. Проверка `isRoomHost` корректно передает права новому устройству.

### 4.2. Ручная передача ведущего (`transferHost`)
- Реализована для комнат голосового канала Discord (`POST /api/activity/rooms/:id/host`).
- **Граничные проверки:**
  - Передать может только текущий ведущий (`isRoomHost`).
  - Целевой пользователь должен присутствовать в комнате (в `members` или `watchers`).
  - Запрещена передача на `guest` или `shared` (`Ведущим может быть только участник с аккаунтом`).

## 5. Обнаруженные краевые дефекты и риски

В ходе глубокого анализа и тестирования исходного кода выявлены следующие нюансы и дефекты:

### ⚠️ Дефект № 1: Проблема «осиротевших комнат» (Orphaned Room Zombie State)
- **Где находится:** `website/src/services/rooms.js`, строки 512–522
- **Суть проблемы:**
  В функции `adoptIfHostAbsent` стоит жесткая проверка:
  ```javascript
  if (!room.channel_id || !user || !user.id || user.id === "guest" || user.id === "shared") return;
  ```
  Это означает, что «усыновление» брошенной комнаты работает **только для комнат голосового канала Discord** (`room.channel_id !== null`).
- **Как воспроизводится в обычной комнате:**
  1. Пользователь 1 создал обычную комнату по коду и вышел. Комната опустела (`members.size === 0`).
  2. Через 60 секунд срабатывает таймер `promoteIfHostGone`, но так как `members.size === 0`, ведущий никому не передается.
  3. Через 5 минут в комнату по коду заходит Пользователь 2.
  4. Так как `room.channel_id === null`, `adoptIfHostAbsent` завершается досрочно.
  5. В `joinRoom` вызов `promoteIfHostGone` отсутствует.
  6. **Результат:** Ведущим комнаты остается отсутствующий Пользователь 1 (`host_client_id = null`). Пользователь 2 числится гостем. Пользователь 2 **не может включить фильм, перематывать или ставить на паузу**, получая ошибку `«Фильм выбирает только тот, кто создал комнату»`. Комната оказывается парализована до ее полного удаления через 30 минут.

### ⚠️ Дефект № 2: Отсутствие ручной смены хоста в обычном API
- В `website/src/routes/rooms.js` нет маршрута для добровольной передачи прав ведущего другому участнику (например, `POST /api/rooms/:id/host`), в то время как в Activity такой маршрут есть. Если ведущий хочет передать управление другу в обычном приложении, ему приходится полностью закрывать приложение и ждать 60 секунд.

### ⚠️ Дефект № 3: Неработоспособность режима `controls: "all"`
- В `website/src/services/rooms.js`, строки 708–720:
  ```javascript
  if (room.controls === "host" && !isHost) {
    return { ok: false, error: "Только ведущий может управлять воспроизведением." };
  }
  if (!isHost && ["play", "pause", "seek", "rate"].includes(action.type)) {
    return { ok: false, error: ... };
  }
  ```
  Второе условие блокирует паузу, перемотку и скорость для всех негостов независимо от того, выставлено ли в комнате `controls: "all"` или `"host"`. Настройка комнаты `controls` фактически игнорируется.

## 6. Рекомендации по исправлению

### Решение для Дефекта № 1 (Осиротевшие комнаты):
В `website/src/services/rooms.js` разрешить `adoptIfHostAbsent` назначать хостом первого вошедшего в пустую комнату пользователя с аккаунтом даже при `room.channel_id === null`:

```javascript
function adoptIfHostAbsent(room, user, clientId) {
  if (!user || !user.id || user.id === "guest" || user.id === "shared") return;
  if (hostPresent(room)) {
    room.host_absent_since = 0;
    return;
  }
  const since = room.host_absent_since || room.empty_since;
  if (!since || Date.now() - since < HOST_GRACE_MS) return;
  setHost(room, { id: user.id, name: user.name }, clientId);
}
```
А при общем пароле (`shared`), если в пустую комнату входит устройство, когда прошлого создателя нет дольше `HOST_GRACE_MS`, назначать его `host_client_id`.

## 7. Разбор и исправления (07.11)

- **Дефект 1 — подтверждён, исправлен.** `adoptIfHostAbsent` работает и в обычных комнатах: вошедший через минуту после ухода ведущего становится ведущим. Комната, в которую ещё никто не заходил (`had_members`), за создателем сохраняется — иначе друг с кодом перехватил бы комнату, пока создатель открывает поток. При общем пароле ведущим может стать устройство (нужен `client_id`).
- **Дефект 2 — подтверждён, исправлен.** `POST /api/rooms/:id/host` (`user_id` или `key` отпечаток устройства — при общем пароле id у всех один; `client_id` — своё устройство). `transferHost` теперь работает и вне Activity. Кнопки в приложениях не добавлены.
- **Дефект 3 — не дефект.** Блокировка `play/pause/seek/rate` для гостей задумана (пауза гостя остаётся у него на компьютере, клиенты на это рассчитаны); `controls` ограничивает остальное. Менять только вместе с четырьмя клиентами.
- **Срок и код.** Пустая комната живёт 5 минут (`EMPTY_ROOM_TTL_MS`), очистка раз в 30 с (раньше 5 мин — реальный срок был до 10). Код обычной комнаты — 6 цифр, как в Activity (`shortRoomId`). Из-за короткого кода просмотр и вход в комнату ограничены `roomLookupLimiter` (40 в минуту).
