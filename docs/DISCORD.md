# Интеграция с Discord — проект

Статус (30.10.2026): вход через Discord, вход устройств по коду, совместный просмотр (ПК, Android, Samsung TV), прогресс
по аккаунту, «Мои фильмы» и активность в Discord (ПК) — сделаны. Своих библиотек нет: все видят всю медиатеку. Ниже
сначала — что сделано на деле (§0), дальше — исходный план 20.10; где сделано иначе, сказано в §0.

## 0. Как сделано (отличия от плана)

**Вход** (`website/src/routes/auth.js`, `services/discord.js`, `services/users.js`)
- OAuth2, scope `identify`, токен Discord отзывается сразу после запроса профиля. Роли — ботом, раз в 15 минут.
- Порядок проверки: `DISCORD_OWNER_ID` (всегда админ) → `DISCORD_ALLOWED_USERS` → бот (`DISCORD_ROLE_ADMIN` / `DISCORD_ROLE_ALLOW`;
  без списка ролей — любой участник сервера). **Если бот и белый список не заданы — входит только `DISCORD_OWNER_ID`** (с 2.5.2; раньше пускали любого).
- Бот онлайн не нужен (только REST «участник по id»), поэтому в Discord он «не в сети» — это нормально.
- После входа — возврат на страницу, откуда пришли (`?return=`, иначе `Referer`, иначе главная с `SITE_PREFIX`).
- Пароль `SITE_PASSWORD` остаётся запасным входом. `PASSWORD_AUTH_ENABLED=false` закрывает его совсем: новые входы по паролю
  запрещены, а уже вошедшие по паролю (сессии и устройства, привязанные из парольной сессии) выкидываются при следующем запросе.

**Устройства** — как в плане: код `A3F-821` на 10 минут, ссылка `…/link?code=…`, токен устройства (на сервере только хеш).
На сайте окно «Связать устройство» показывает, от чьего имени войдёт устройство, и при входе по паролю предлагает Discord.

**Совместный просмотр** (`services/rooms.js`, `routes/rooms.js`; ПК — `desktop/…/party/`)
- Транспорт — **SSE** (`/api/rooms/:id/events`) + REST-команды, а не WebSocket. Комнаты в памяти, приглашение — код комнаты.
- Управляет только ведущий (создатель): фильм, пауза, продолжение, перемотка. Участник может поставить паузу только у себя.
- Участник = открытый поток событий. Пусто — пауза. Кто-то грузится — комната ждёт (`waiting`, не дольше 30 с на участника,
  а не 10 с, как в плане): догонять перемотками на медленной сети не получилось (чёрный экран).
- Комнаты есть на ПК, Android (2.5.0) и Samsung TV; на сайте нет. С 2.7.0 гость по «Смотреть вместе» сразу попадает в плеер
  на файле и месте ведущего; ведущий закрыл плеер — у гостей он закрывается (`change_file` с `file: null`).

**Активность в Discord (ПК)** — `desktop/…/discord/DiscordRpc.kt`, ID приложения приходит с сервера (`discord_client_id`).

**Не сделано**
- Роль `admin`: удаляет любые раздачи (`removeChecker`: остальные — только свои и только недокачанные, `OWNER_LOCK`),
  «Определить через ИИ» для чужих раздач и статистика (`requireAdmin` в `routes/aititle.js`). Личные библиотеки сделаны проще
  плана §2: `services/shelf.js` — только список «Мои фильмы» (без приватных раздач и «скрыть у меня»).
- Перенос старых раздач на пользователя (`adoptDevice`) сравнивает владельца строкой, а в `owners.json` — объект `{dev}`: не переносит.
- Токен устройства не истекает, списка «мои устройства» с отключением нет.
- Вход по паролю даёт роль admin.

Три задачи:
1. Вход через Discord вместо общего пароля, пускать только участников одного сервера с нужной ролью.
2. У каждого пользователя своя библиотека — видимая часть общего аккаунта AllDebrid.
3. Совместный просмотр с синхронизацией таймлайна.

## 0.1. Что было до Discord

- Вход — один общий пароль `SITE_PASSWORD` → сессия `movieportal.sid` (`requireLogin`). Личности пользователя нет.
- «Личное» держится на cookie устройства `sdev`: избранное и `owners.json` (кто добавил раздачу, тот может удалить).
- Один ключ `ALLDEBRID_API_KEY`; `/api/library` отдаёт всем всё.
- Подпись зеркала (`/api/file/mirror-url`) выдаётся на **любую** ссылку, не проверяя, чья она. При личных библиотеках это дыра — закрывается в п. 2.
- Приложения (Android, Android TV, ПК) ходят с той же сессией; браузера на ТВ нет.

## 1. Вход через Discord

### Принцип: токены Discord не хранятся
Discord нужен только чтобы **один раз узнать, кто это**. Токен пользователя живёт несколько секунд внутри обработчика входа и выбрасывается; на диск, в сессию и в журнал он не попадает.
Роли проверяет **бот** своим токеном (`DISCORD_BOT_TOKEN` в `.env`), а не токеном пользователя — поэтому хранить `refresh_token` не нужно.
Сессия после входа — **наша** (`movieportal.sid`, как сейчас), к Discord она не привязана.

Что хранится о пользователе: `discord_id`, имя и хеш аватара (для показа), роль, `created_at`, `last_seen`, `role_checked_at`. Больше ничего.

### Поток входа
OAuth2 Authorization Code, scope **только `identify`**. Сервер — конфиденциальный клиент (секрет на сервере), защита от подмены — одноразовый `state` в сессии.

1. `GET /auth/discord/start` → случайный `state` в сессию → редирект на Discord.
2. `GET /auth/discord/callback?code&state` → `state` сверен и удалён → код обменян на `access_token` → `GET /users/@me` → получен `discord_id`.
3. Токен сразу отзывается (`POST /oauth2/token/revoke`) и забывается. `refresh_token` не сохраняется.
4. Бот: `GET /guilds/{DISCORD_GUILD_ID}/members/{discord_id}`.
   - 404 (не участник) или нет роли из `DISCORD_ROLE_ALLOW` → страница «доступ закрыт», сессия не создаётся.
   - Иначе: создать/обновить запись `users`, `session.regenerate()`, в сессию — только `uid`.

Переменные окружения (только `.env`, в репозиторий не попадают):
`DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_BOT_TOKEN`, `DISCORD_GUILD_ID`, `DISCORD_ROLE_ALLOW` (список id ролей), `DISCORD_ROLE_ADMIN`.
Адрес возврата (`redirect_uri`) собирается из домена сайта в `.env` и должен совпадать с адресом в Developer Portal; сам домен в репозиторий не пишем.

### Бот
- Приложение в Discord Developer Portal, к нему бот; бот добавлен на сервер **без разрешений** (scope `bot`, права 0).
- Достаточно REST-запроса «участник по id» — держать бота онлайн (gateway) и включать привилегированный intent `GUILD_MEMBERS` не нужно: он требуется только для списка всех участников и событий о них.
- Запросы бота — через общую функцию с учётом лимитов Discord (`429` → `retry_after`). Пользователей десятки, нагрузка ничтожная.

### Роли
- `ALLOW` — смотреть и добавлять.
- `ADMIN` — видеть всё, удалять чужое, управлять доступом.
Роль берётся из ответа бота при каждой проверке и пишется в `users.role` (у кого обе — `ADMIN`).

### Перепроверка роли и отзыв доступа
- Проверка «лениво» при запросе: если `role_checked_at` старше **15 минут**, сервер в фоне спрашивает бота; запрос пользователя не ждёт.
- Плюс раз в час проход по пользователям, которые были активны за последние сутки (у них может быть открыт только WebSocket комнаты).
- Ответ 404 или нет роли → гасим все сессии и токены устройств этого `uid`, закрываем его WebSocket-подключения, выходим из комнат.
- Discord недоступен (сеть, 5xx) → **не** выгоняем: продолжаем с последней известной ролью до 24 ч, в журнал — предупреждение. Это защищает от выключения всех при сбое Discord.
- Итог: снятая роль действует максимум через ~15 минут (активный пользователь) или через час (только комната). Мгновенный отзыв — только с gateway и `GUILD_MEMBERS` (см. этап 6).

### Приложения: device flow
Android TV не имеет нормального браузера, на ПК и телефоне встраивать OAuth неудобно. Поэтому:
1. Приложение: `POST /api/auth/device` → `{code: "ABCD-1234", url, interval}`.
2. Показывает код и QR; пользователь открывает `url` на любом устройстве, входит через Discord, вводит код.
3. Приложение опрашивает `POST /api/auth/device/poll`, получает долгоживущий токен устройства (хранится в Keystore / в защищённом хранилище ПК).
4. Токен устройства — **наш** случайный токен, не Discord: на сервере только его хеш, запись `devices(user_id, token_hash, name, last_seen)`; в настройках можно «выйти на всех устройствах».
5. Запросы с токеном устройства проходят ту же перепроверку роли: снятая роль гасит и токены устройств.

Редирект-адреса OAuth — фиксированный белый список (только сайт), приложения своих redirect_uri не получают.

### Миграция
- На время беты `SITE_PASSWORD` остаётся запасным входом (и для владельца, если Discord недоступен). Отключается флагом.
- При первом входе через Discord текущее устройство (`sdev`) «усыновляется»: его избранное и `owners.json` переезжают на `user_id`. Старый `sdev` дальше не нужен.

## 2. Личные библиотеки

AllDebrid-аккаунт один, файлы в нём общие. Задача — **кто что видит**, а не отдельные хранилища.

### Модель
```
users(id, discord_id, name, avatar, role, role_checked_at, created_at, last_seen)  -- без токенов Discord
magnets(ad_id, hash, added_by, visibility, added_at)      -- visibility: server | private
shelf(user_id, ad_id, hidden, favorite, progress_json)    -- личное состояние
```
- **Видимость раздачи**: `server` — видят все с ролью, `private` — только добавивший (и админ).
- **Личные отметки**: «скрыть у меня», избранное, прогресс просмотра — в `shelf`, на пользователя.
- Новая раздача получает видимость по умолчанию (настройка, см. вопросы).
- Старые раздачи (до Discord) = `server`, `added_by` берём из `owners.json`, иначе владелец.
- Повторное добавление уже существующего хеша: AllDebrid вернёт тот же id → просто добавляем в `shelf`, а не плодим дубль.
- Удаление из AllDebrid: только `added_by` или админ, и только если у раздачи нет других «полок» (иначе — убрать только у себя).

### Где проверять (всё на сервере, клиенту не доверяем)
Единая функция `canSee(user, adId)` в: `/api/library`, `/api/magnets/:id`, `…/files`, `/api/file/unlock`, `/api/file/mirror-url`, `/api/playlist`, удаление.
Для `mirror-url` и `file/unlock` нужен индекс **ссылка → раздача** (строится из `treeCache`); неизвестная ссылка → 404.
Подписанный адрес зеркала остаётся как есть (внешние плееры без cookie), живёт 12 ч. В подпись добавить `uid` — для журнала и отзыва: когда бот сообщил, что роль снята, зеркало отклоняет подписи этого `uid` (иначе ссылка проработала бы ещё до 12 ч).

### Хранилище
Сейчас всё в JSON. Для users/magnets/shelf — **SQLite** (`better-sqlite3`): пользователей десятки, но нужны согласованные связи и транзакции. Сессии и кэши остаются как есть.

## 3. Совместный просмотр

### Идея
Сервер — только источник правды о «состоянии комнаты»; видео каждый качает со своего `BurstProxy` по своему подписанному адресу. Файл идентифицируется **не URL**, а `(ad_id, file_idx)`.

### Транспорт
WebSocket `/ws/party` (библиотека `ws`). nginx без http2 — это нормально, нужны только заголовки `Upgrade/Connection` и `proxy_read_timeout` ≥ 1 ч. Аутентификация — сессия или токен устройства, проверка `Origin`.

Комната: `party(id, host_user, file, state, members, controls)`. Приглашение — ссылка `https://<сайт>/r/<id>` (id случайный, 128 бит), её можно кинуть в Discord; открыть может только участник сервера с ролью.

### Состояние и сообщения
```
state = { file:{ad_id, idx}, playing, pos, rate, anchor_server_ms, seq }
```
Позиция сейчас: `pos + (serverNow − anchor) * rate`, если `playing`, иначе `pos`.

Клиент → сервер: `play`, `pause`, `seek(pos)`, `rate`, `buffering(true/false)`, `ping`.
Сервер → всем: новое `state` (с растущим `seq`), список участников, события «вошёл/вышел».
Кто может управлять — настройка комнаты: `host` или `все`.

### Часы
При входе и каждые ~30 с: 4–5 ping/pong, берём замер с минимальным RTT → `offset = serverTime − (t0 + rtt/2)`. Дальше всё считаем в серверном времени.

### Подгонка (контроллер дрейфа)
Раз в 500 мс клиент считает `drift = localPos − targetPos`:
- `|drift| < 0.3 с` — ничего;
- `0.3…2 с` — мягко меняем скорость на 0.95/1.05 (mpv `speed`, VLC `rate`, Media3 `setPlaybackParameters`), пока не сойдётся;
- `> 2 с` — `seek`.
Пользовательская перемотка и пауза → `seek`/`pause` в комнату; свои локальные подстройки в комнату **не** отправляются (иначе петля).

### Буферизация
Если у кого-то `buffering`, комната на паузе («ждём Имя»), максимум 10 с, потом едем дальше — такой участник догоняет сам. Режим «ждать всех» можно выключить.

### Что своё у каждого
Дорожка звука, субтитры, громкость, движок (mpv/VLC/Media3), качество — локально.

### Код
- `shared/…/party/`: чистая логика без UI — `PartyClock` (offset), `DriftController`, `PartyState`, протокол сообщений. Тесты в `shared/src/test` (`shared.yml` их запускает).
- Интерфейс `SyncPlayer { position; seek(ms); setRate(r); play(); pause(); isBuffering }`.
  Адаптеры: ПК — за `PlayerEngine`; Android — `PlayerActivity` для Media3 и VLC (на Blu-ray позицию берём из `TsClock`/`TsPlayback`).
- UI: кнопка «Смотреть вместе» в плеере, список участников, ссылка-приглашение.
- Web: то же на `<video>`, если сайт играет видео в браузере.

### Права на файл
Участник комнаты может видеть файл, которого нет в его библиотеке? Предлагаю **да, на время комнаты**: сервер выдаёт подпись зеркала для файла комнаты любому её участнику с ролью. Файл не появляется в его библиотеке.

## 4. Безопасность

- Одноразовый `state`, один фиксированный redirect_uri, `httpOnly`; rate-limit на `/auth/*` и WS-подключения.
- Cookie сессии сейчас `SameSite=Strict`: при возврате с discord.com браузер её не пришлёт и `state` не сверится. Нужно `Lax` (или отдельная короткая cookie только для `state`).
- Токены Discord пользователя **не хранятся** (используются один раз и отзываются). Токен бота — только в `.env`. Токены устройств — только хеши. Ничего из этого не пишется в журнал.
- Любой запрос к файлу проходит `canSee`; WS-команды проверяют членство в комнате.
- Нельзя заменять зеркало прямыми ссылками AllDebrid (постоянное правило).
- Журнал: вход, отказ по роли, отзыв, создание комнаты.

## 6. Открытые вопросы (решает владелец; ниже — предложения)

1. **Видимость по умолчанию** для новых раздач: все или только я? Предложение: для всех (`server`), галочка «только мне» при добавлении.
2. **Старые раздачи** — общие для всех? Предложение: да.
3. **Кто удаляет** из AllDebrid: добавивший + админ? Предложение: да; остальные только убирают у себя.
4. **Управление в комнате**: только хозяин или все? Предложение: настройка комнаты, по умолчанию все.
5. **Ожидание при буферизации**: ждать всех по умолчанию? Предложение: да, до 10 с.
6. **Сохранить пароль** как запасной вход после перехода? Предложение: да, на время беты, потом выключить флагом.
7. **Как быстро** отзывать доступ при снятии роли? Предложение: хватит 15 мин / 1 ч (бот только по REST); мгновенный отзыв через gateway — этап 6, если понадобится.
8. **Что нужно от владельца**: создать приложение и бота в Discord Developer Portal, добавить бота на сервер без прав, прислать в `.env` сервера id гильдии, id ролей, client id/secret и токен бота (в репозиторий не пишем).
9. Ответы перенести в CLAUDE.md — они закрывают висящий вопрос «кто может входить, кто управляет комнатой, порядок работ».
